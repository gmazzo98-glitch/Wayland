# I30 - Deep-profile orchestrator

## What I built

- `intel/budget.py`: hard run-level limits for wall-clock time, LLM tokens, rounds, collector count and coverage target, with serialisable snapshots.
- `intel/orchestrator.py`: capability-aware planning, bounded parallel collector execution, resource-governor slots for worker-backed steps, verification before ledger merge, per-collector checkpointing, optional LLM follow-up queries, coverage/unknown reporting, and `CompanySourceRun` status mirroring when a database session is supplied.
- `tests/test_intel_orchestrator.py`: offline tests for budgets, capability planning, parallel merge/checkpoints, verification, worker-adapter execution, optional follow-up failure and checklist coverage.

The implementation writes only the existing `crawler_deep_profile` ledger and existing `CompanySourceRun` rows. It does not write scores, weights, `SignalRecord`, or `company_people`.

The roadmap baseline remains 11 of 42 facts held (23% weighted overall; 2 facts / 3% from the crawler/web layer). No new accepted golden score is reported: the live orchestrator smoke run was incomplete and did not run the required `intel_gap.py --require-ticket I30` acceptance command.

## Decisions taken and why

- Default run budget is approximately 250,000 LLM tokens and 15 minutes, matching the roadmap.
- The orchestrator skips collectors whose capabilities are missing. A collector declaring `worker` is skipped unless the existing worker queue is injected as `worker_runner`; this prevents silently running a helper-PC task on the app server.
- Verification is called before facts are merged. If a source cannot be refetched, the fact remains in the ledger with the verifier's unverified decision rather than being silently promoted.
- Coverage is category-based and treats `checked_absent` separately from never-checked categories.

## Not done / open points

- The full ASCO 70% web-only acceptance target was not reached or measured.
- Three other-company full-collector runs, a real process kill/resume proof, and a real worker claim/failover test were not completed in this session. The offline checkpoint-resume and injected worker-adapter tests are now covered by the focused suite.
- Existing collectors do not yet expose a common follow-up-query input, so the LLM planner records queries in the next round's company context; collectors that do not consume that field will not benefit until their own tickets add support.
- The orchestrator is not wired into the Streamlit UI or batch runner; those are separate release/surface decisions.

## New tickets proposed

- Add a small adapter around `crawl_jobs`/`worker_hub` that supplies the `worker_runner` contract and records remote target IDs in run metadata.
- Add an orchestrator acceptance harness that runs all completed collectors against the development golden set and proves kill/resume without waiting on Streamlit.

## What the next agent must know

`DeepProfileOrchestrator.run()` is the public entry point. Pass `fetch`, `search`, `llm`, and a worker-queue adapter as dependencies; pass `checkpoint_path` for resumability. The orchestrator is deliberately database-optional for fixture tests, and persistence is opt-in through `db` or `session_factory`.
