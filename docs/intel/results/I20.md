# I20 — Italian registry and institutional lookups (INI-PEC, Registro Imprese, UIBM, ANAC, RNA)

Agent: `vibe-a3f7` · branch `intel/I20-italian-registry-and` · write scope: `intel/collectors/registry_it.py`, `tests/test_intel_registry_it.py`, `docs/intel/results/I20.md`

## What I built

- `intel/collectors/registry_it.py` — the `registry-it` collector:
  * **Institutional imprint from the company's own site** (grade B, quote-grounded): C.F./P.IVA (`identity.vat`), REA (`identity.rea`), share capital with the fully-paid marker (`identity.share_capital`), registered office (`identity.registered_office`, anchored: the company's brand must appear within 200 characters of the address, so a GROUP footer's "Sede Legale" is never taken for a subsidiary's office), PEC (`contact.pec`, including generic `@pec`/`@legalmail`/`@postacert` addresses).
  * **Public revenue history** (grade C): candidates from (1) the I05 search layer when its providers are reachable and (2) the public directories' own search endpoints (`DIRECTORY_SEARCHES`, currently the feasibility-verified topaziende.quotidiano.net WordPress search) — a directory is a source plugin: verify live, then add as data; no page URL is ever guessed. The page must NAME the target company (brand-word gate) before its table is used; ≥3 years required; the quote is the verbatim first table row.
  * Honest `checked_absent` per key when the site/directories were read and nothing was found; honest errors otherwise; nothing bought, no simulated values.
- `tests/test_intel_registry_it.py` — 9 offline tests (recorded pages, no network): full imprint extraction, quote grounding + ledger validation, absence, no-website error, revenue series from a directory page, ≥3-year rule, **a directory page about a different company is rejected** (regression for a real false-positive the live Isolcell run caught), graceful behaviour without a search client, prefix discipline.

## Decisions taken and why

- Grade B for imprint facts even though they restate registry data: the company's own publication is the evidence the collector actually holds; upgrading to grade A needs a feasible register (none is, from this environment).
- The revenue history is grade C (a public third-party directory), explicitly NOT `financials.*` grade A (the roadmap's "grade A only" applies to registry-filed accounts, which remain infeasible).
- Directory search endpoints are data (`DIRECTORY_SEARCHES`), not code, and each must be feasibility-verified before being added — the plugin-authoring rule from I16 applied here.
- `live_db_read` was listed in the ticket's needs but no `.env` exists in this sandbox; the ticket's acceptance (golden capture + feasibility table) was provable web-only (`--corpus-file ... --web-only`). The DB-side baseline for ID-01 is already covered by I01's original scoring work.
